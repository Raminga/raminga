Status: Living document · 更新：2026-11-12

本清单汇总 Raminga **预期要实现的全部功能**，以及每项的设计要点和当前状态，作为项目范围的总表。测试方法、G4 阈值摘要与当前验证边界见 [testing.md](testing.md)。

> **当前阶段：** 第一版三步中的第 1 步（网络连接）和第 2 步（内容发布、好友列表、查看/下载）代码已完成，第 3 步（Agent/DSH）进行中：插件外壳与真实宿主验收部分完成，发布流水线已实现，尚未首发，预发布安装冒烟未完成。连接、内容、好友表有单元、本机集成和 Docker 证据（`/disconnect` 只有本地证据）；真实网络只有一次手工报告称直连公网服务器验证通过（2026-11-06～07，具体项目未单独记录），经中继、打洞、DHT 回退、好友列表找节点仍 NOT_TESTED。关注、动态流、好友申请等完整社交功能未实现；Docker 结果不等于公网或生产可用。

## 第一版路线（当前执行入口）

2026-11-05 确定：第一版只做三步，**网络连接 → 内容分发 → Agent 调用**。功能和技术方案都写在本节。下面各节的表格仍是完整功能总表，不在这里列出的功能都留到第一版之后，包括已设计但未实现的项。

**整体规则：** 第一版不设不公开的内容。当前节点关联的档案、动态和好友列表全部公开。

### 第一版功能

**1. 网络连接**

- 保留现有的连接、中继、打洞和聊天。
- `/disconnect` 之后，中继不再自动连回来。
- 公告地址过滤掉外部连不上的地址。

现状：真实网络在 IPv6 防火墙场景 M6-D PASS ×1。IPv4 NAT 打洞、M6-R、可复现性、对称 NAT / CGNAT、Windows 清单冒烟可以并行补测，不挡后面的步骤，未测的保持 NOT_TESTED。

**2. 发布内容**

- 用户可以发布自己的档案、动态和好友列表，发布后别人能拿到。

**3. 好友列表**

好友列表和电话簿、关注列表在第一版是同一张表。

- 每条包含名字、Peer ID、地址、描述，全部公开。
- 地址只放公网地址和中继地址；地址可以落后。
- 名字和描述可以设置，只有表里的节点才能设置。描述用于说明这个节点的特征。
- 只要发生过 Raminga 层面的往来（连接、聊天、查看内容、预约中继），**双方都进表**；只有 DHT 路由流量的都不进表。
- 可以把节点移除；对方之后如果又有往来，会重新进表。别人已经看到的无法收回。
- 名字和描述只是列表主人的说法，显示时要注明来源，不覆盖查看者自己的记录。

**4. 查看别人的内容**

- 查看某个节点的档案、动态和好友列表，并下载文件。
- 从好友列表里选一个节点去连接。地址连不上时，自动用 DHT 查最新地址。
- 读到列表不会自动连接，只有用户或 Agent 选中时才连。

**5. Agent**

- Agent 通过本地 API 完成上面这些操作：发布内容、查看内容、读好友列表，再去访问列表里的节点。
- DSH 插件是接入这个 API 的方式。不另做内置 AI 宠物。
- 持久运行、入站唤醒与自动回复属于宿主 Agent 的内部设计，不进入 Raminga daemon，也不在插件范围。插件提供 Node API、MCP/DSH 工具、单一来源 Skill 与私有数据初始化。

### 不做

不公开的内容、关注、动态流、缓存、好友申请、拉黑、聊天发文件、内容转发、多设备、密钥备份、签名公证和安装渠道。

### 接受的限制

- 发布者离线时，内容拿不到。
- 只能经中继连接的节点，只能拿到小内容，大文件需要直连。
- 查看别人时，对方能看到你的 Peer ID 和 IP，双方都会进表，所以浏览记录是公开的。
- 爬虫逛一圈也会进被访问节点的表；主动 `/connect` 过的节点受保护，不会被挤掉。

### 已知问题（暂不实现）

- 首次创建身份时明确提示：当前 `raminga` 自动新建身份时不提示，迁移顺序出错时 Peer ID 会悄悄变化（2026-11-06 实际发生）。

### 第一版验收标准

在真实网络的设备上：

1. A 发布档案、动态，并有好友列表；B 能看到并下载。
2. B 通过 A 的好友列表找到 C，看到 C 的内容，包括 B 没用过 C 的中继的情况。
3. Agent 通过本地 API 走一遍同样的流程。

Docker 结果不能代替这项验收。Agent 插件作为后续步骤并行推进。第一版**尚未完成**：第 3 步的发布与真实安装验收、上述真实网络验收都还未完成。

### 第一版技术方案（2026-11-05）

> **实现状态（2026-11-12）：** 第 1、2 步代码已完成（第一版形式）。第 3 步已有 Claude/Codex/DSH 插件外壳、单一来源 Skill/数据模板与真实宿主验证（Claude 安装/权限/首次使用/漫游、Codex 安装/onboarding/只读工具、DSH 临时 profile + 真实模型）；持久宿主运行与宿主审批不在插件范围，Windows 与预发布安装冒烟仍未完成；发布流水线已实现，尚未首发。真实网络的其他限制按测试记录，不得由本机 Agent E2E 外推。

**跨节点协议：** Raminga 自己的跨节点协议（聊天和内容）统一改成 HTTP，跑在 libp2p 数据流上，请求体用 JSON。DHT、中继、打洞这些 libp2p 自带协议，以及本地 API（Connect-RPC）不变。聊天和内容已于 2026-11-06 实现。

**实现方式：** 使用标准库 `net/http` 加 go-libp2p 的 `p2p/net/gostream`，请求时带 `network.WithAllowLimitedConn`。不用 `p2p/http`（`libp2phttp`），依据是下面的小测试。

| 接口 | 作用 |
| --- | --- |
| `POST /chat` | 发消息，返回成功即 ACK；离线待发和去重继续用现有逻辑 |
| `GET /manifest` | 取清单：档案、动态和好友列表，带版本号 |
| `GET /files/<路径>` | 下载文件，支持 `Range` 断点续传 |
| `/connect` 成功后的一个小请求（路径实现时确定） | 通知对方这是 Raminga 层面的连接，对方才进表 |

**发布：**

- 公开内容统一放在 `public/`：`profile/`、`posts/` 和程序生成的只读文件 `friends.json`（手动修改会被覆盖）。
- 文件类型不限。默认单文件 ≤100 MB、`posts/` ≤1 GB、`profile/` ≤10 MB，可配置；超出的不发布并提示。
- 用 `os.Root` 限制只读公开目录；符号链接和隐藏文件不发布。
- 有人来取时才扫描，结果缓存几十秒，哈希按"大小 + 修改时间"复用。下载时文件被改导致哈希不符，由下载方提示重试。
- 第一版不签名，只校验文件哈希：内容只由发布者提供，libp2p 连接已校验 Peer ID。以后支持转发时再加签名。

**好友表：**

- SQLite 新建一张表，存名字、Peer ID、地址、描述和内部用的时间，`friends.json` 只包含前 4 项。SQLite 是唯一的准确来源，`friends.json` 可随时重建。名字合并进来后去掉 `peer_names`。不复用 `known_peers`。
- 写入时机：`/connect`、聊天、查看内容、预约中继，双方都记录；只有 DHT 路由的连接不记录。入站连接看不出用途，所以 `/connect` 成功后要发一个小请求通知对方；聊天和查看内容本身就是请求；预约通过 go-libp2p 中继的 `WithACL` 感知，待接入。
- 记下的地址是对方自己声称的，公开前过滤；读取方同样过滤并限制尝试次数，连接时校验 Peer ID。
- 只有表里的节点才能设置名字和描述。每个节点一个名字，名字在本地不能重复。
- 同步：不要求严格一致，尽量少占资源。每 10 分钟检查一次，增删好友或名字、地址、描述有变化才整份重写（先写临时文件再原子替换，流式生成）；启动时重新生成一次。可手动触发立即同步（命令待实现时确定）。
- 读取时直接发送 `friends.json`，不查 SQLite。聊天只更新内部往来时间，不算变化；同一节点的往来时间至多每 10 分钟写一次。
- 默认最多 10,000 条，超出时先删最久没往来的；主动 `/connect` 过的不自动删除。
- 节点自己的名字和介绍不进好友表，从档案取：`profile/index.md` 的第一个标题作为名字，正文作为介绍，没有就显示 Peer ID。

**连接：**

- 已知地址全部失败后查 DHT：先读对方上报的地址记录，再用现有的 `FindPeer`。查到就重连并更新好友表，总等待时间有上限。现有代码只在完全没有地址时才查 DHT，需要修改。
- 节点主动把自己的地址上报到 DHT：地址变化时写一次，平时定期刷新。NAT 后的节点同样上报，但不进路由表，也不保存别人的记录。
  - 现成能力：`go-libp2p-kad-dht` 的 `PutValue`/`GetValue` 和 `NamespacedValidator`，go-libp2p 的签名 `PeerRecord`。现有代码用 `DisableValues()` 关闭了值存储，需要打开。
  - Raminga 只写校验规则和上报逻辑：签名有效、Peer ID 与键一致、大小不超限、多个版本选序号最大的。
  - DHT 服务端的记录在内存里，重启后等节点下次刷新恢复；要限制大小和保存时间，并补恶意写入测试。
  - 依赖一台可公网访问的 DHT 服务端保存记录，第一版使用一台可公网访问的 DHT 服务端。
- `/disconnect` 加持久化的暂停标记，中继预约循环跳过，直到再次 `/connect`。
- 重启恢复：现有逻辑启动时只把缓存的地址读进内存，不会连回去。第一版改成启动时自动连回主动 `/connect` 过、且支持中继或 DHT 服务端的节点，最多 3 个，跳过已暂停的。不写配置；配置里已有的预置节点继续生效。

**经中继：** 只取清单和 ≤64 KB 的小文件。更大的先等打洞升级成直连，升级不了就提示需要直连，不用多条中继连接拼接下载。好友列表超过 64 KB 时同样等直连。

**查看：** 下载到 `downloads/<Peer ID>/`，文件名先清理，不能跳出目录。TUI 只把 Markdown 和纯文本显示成文字，其他格式提示保存位置。

**访问控制：** 第一版不限制谁能读取，只按 Peer ID 限速和限制并发。HTTP 服务端要配超时和大小限制，并补上相应的恶意输入测试。

**本地 API：** Connect-RPC 新增查看好友、设置描述、移除、取清单、下载（推送进度）。TUI 和 DSH 插件共用。

**Agent：** 和人使用同样的功能，不区分角色。

**实施顺序：** 第 1 步内完成好友表基础（重启恢复和断开暂停依赖它，暂不对外公开）、两个修复、重启恢复和 DHT 地址上报与回退。第 2 步先改聊天，因为有现成测试可以对照，再做双方进表和内容。改完后聊天要在真实网络重新验证。

#### 小测试结果（只在本机回环，不代表真实网络）

2026-11-05，go-libp2p v0.51.0，同一台机器上的三个节点；发起方 A 没有在中继 R 上预约，连接确认为受限连接。命令：`go test -count=1 -v -timeout 120s ./.local/spike-http-relay/`（测试文件被 Git 忽略，未入库）。

| 场景 | 结果 |
| --- | --- |
| `libp2phttp`，默认或只带允许受限连接的标记 | FAIL：10 秒超时，源码在无截止时间或超过 10 秒时替换了 context |
| `libp2phttp`，带标记且截止时间 5 秒 | PASS |
| `libp2phttp` 的 `NamespacedClient` | FAIL：受限连接上取协议元数据超时 |
| `net/http` + `gostream`：GET、POST JSON、服务端取到 Peer ID、`Range` 206 | PASS |
| 经中继下载 1 MiB | 按预期失败：收到 98,304 字节后连接被重置 |
| 重置后再次 POST | PASS，无需手动恢复 |
| 直连下载 1 MiB（SHA-256 校验）和从中点续传 | PASS |

| 新发布的文件可能要请求两次才看得到 | 清单缓存过期后，`Snapshot` 先返回旧清单，同时在后台重新扫描，旧清单年龄没有上限；也没有手动重新扫描的入口（读代码确认，未实测） | 过期后的请求等待这次扫描完成；加手动重新扫描入口，可与 `/published` 一起做 |

## 1. 网络与连接

| 功能 | 设计要点 | 状态 |
| --- | --- | --- |
| 传输 | go-libp2p v0.51.0；TCP + QUIC；默认同时监听 IPv4 与 IPv6（`0.0.0.0`、`::`），同一端口 | ✅ 真实网络 |
| 中继（Circuit Relay v2） | 客户端默认开启；服务端（provider）默认关闭，需 `--relay-provider` 显式开启并有配额；中继连接受 go-libp2p 默认限制（2 分钟 / 128 KiB） | ✅ 真实网络 |
| 打洞（DCUtR） | 经中继建立受限连接后协调打洞；QUIC/UDP 成功率高，TCP 打洞通常失败 | ✅ 真实网络（IPv6 防火墙，1 次）；IPv4 NAT 未测 |
| 停中继后保持直连 | 直连建立后不再依赖中继；QUIC 每 15 秒保活 | ✅ 真实网络（≥5 小时 45 分） |
| AutoNAT v2 | 判断本机是否可从公网直接访问；没有探测节点时为"未知" | ✅ Docker/本地 |
| 独立 DHT | `/raminga/kad/1.0.0`，不使用公共 IPFS DHT；按 Peer ID 查当前地址（现有机制是问见过目标的节点，不保证查到；第一版增加地址上报） | ✅ Docker/本地 |
| 地址公告 | 配置的 `--announce` 再追加网卡上的公网地址（云服务器 1:1 NAT 只需手写公网 IPv4） | ✅ 真实网络 |
| `/connect` 的中继自动成为候选 | 连上支持中继的节点后立即申请预约，获得中继地址 | ✅ 真实网络 |
| 对称 NAT / CGNAT 诊断 | 打洞失败时如实诊断为"只能走中继" | ✅ Docker；真实网络未测 |
| 不使用 UPnP / NAT-PMP | 绝不静默开启端口映射 | ✅ 规则 |
| 自动发现服务器公网 IPv4 | 用其他节点观察到的地址 + AutoNAT 验证，免去 `--announce` | 💬 待设计 |
| 中继地址同时公告 IPv4/IPv6 形式 | 现在只公告建立预约时使用的那一种 | ⚠️ 已知问题 |
| 公告地址过滤 | 过滤链路本地、未指定、组播、虚拟网卡和多余的 loopback；标准库识别不了过期临时 IPv6 | ✅ 本地（单元测试）；真实网络未复测 |
| 中继预约恢复 | 断开后重连，要等退避结束才恢复预约 | ⚠️ 已知问题 |
| 地址变化后快速恢复 | IPv6 前缀变化、切换网络 | 💬 待设计 |
